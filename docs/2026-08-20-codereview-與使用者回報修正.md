## 第一部分：Code review 的六個發現（commit `0c04240`）

派了兩個獨立審查（一個看未提交變更、一個看整條 AI 管線），六個發現全部成立。
共通點：**正常情況都對，壞在外部服務不照約定的時候**。

### 1. Critical｜「重新判讀」先毀後建 → 資料永久遺失

- **發現**：審查者追 `Reanalyze` 的執行順序。
- **為什麼會發生**：寫的時候只想著成功路徑——先清掉舊的、再要新的，很直覺。
  但 AI 會失敗（當天 Gemini 連續一小時 503），失敗時舊判讀與情緒已經刪了，救不回來。
- **修法**：反過來。**先做完新判讀，成功才覆蓋**；失敗則什麼都不動，畫面顯示
  「先前的判讀結果保留著」。
- **驗證**：趁 Gemini 還在 503 時實際按下重新判讀——判讀時間與情緒都原封不動。

### 2. Critical｜併發判讀撞唯一索引 → 整頁 500

- **發現**：審查者注意到「先查 null、再插入」之間隔著 16–105 秒的 AI 呼叫。
- **為什麼會發生**：使用者等太久按 F5、或開兩個分頁，兩個請求都看到「還沒有判讀」,
  都去插入，第二個撞上 `PhotoAnalyses.PhotoId` 的唯一索引。
- **修法**：catch `DbUpdateException` → 重讀既有那筆繼續用。**那不是錯誤狀態,
  是另一個請求先把結果存好了。**

### 3. 「值相同就是 AI 填的」——這個推論在邏輯上不成立

- **發現**：審查者對照 prompt 內容與判斷式。
- **為什麼會發生**：prompt 明寫「使用者有指定情緒時,moodPick 直接回傳該值」——
  所以**使用者自己選的情緒必然等於上次的判讀結果**。用「值相同」判斷來源,
  會把使用者的選擇全部誤判成 AI 填的,正好與要保護的東西相反。
- **修法**：不做事後推論,明確記錄來源:`MoodProfile.IsAiFilled`(一次 migration)。
- **教訓**：**來源要在寫入當下記錄,不能事後從值反推**——尤其當系統本身就會讓兩種來源
  產生相同的值。

### 4. n8n 的 `{ ok: true, ...spread }`——AI 能覆寫成功旗標

- **為什麼會發生**：JS 物件展開,後面的鍵蓋前面的。`ok: true` 寫在展開之前,
  AI 只要自己回一個 `"ok"` 欄位就能改掉它——**最不可信的輸入決定了成敗判準**。
- **修法**：`{ ...JSON.parse(cleaned), ok: true, model: ... }`,關鍵欄位放展開之後。
- **驗證**：換到 OpenAI 後回應 JSON 尾端出現 `"ok":true,"model":"gpt-4o"`,順序正確。

### 5. 型別不符丟未捕捉例外,違反「不丟例外」契約

- **為什麼會發生**：解析時假設欄位型別正確(`GetBoolean()`、`GetString()`)。
  AI 回陣列、把布林寫成字串、error 給數字——都會炸成 500 而不是回落。
- **修法**：型別一律先驗再取(`ValueKind` 檢查)。補 14 項測試,
  **其中型別不符那幾條在修之前是真的會丟例外的**,不是補形式。

### 6. `songs` 沒有上限 = 配額炸彈

- **為什麼會發生**：prompt 要 5 首就假設回 5 首。模型漂移回 40 首的話,
  一次燒 4,000 單位 YouTube 配額(一天只有 10,000)。
- **修法**：`GetSongs` 加 `Take(5)`。**對外部輸入的數量假設都要有上限。**

另有三個小修正：`Pick` 的 Topic 規則改為「Topic 且含歌手名 > 含歌手名 > 任何 Topic > 第一筆」
（翻唱歌手也有自己的 Topic 頻道）；YouTube 快取鍵轉小寫；`SavePlaylist` 驗證失敗重繪時
補回 `AnalyzedAt`。

## 第二部分：使用者回報的 8 項（commit 見 git log 2026-08-20）

### 1. 右上「收藏庫」沒有功能

`_Layout.cshtml` 那是一個純 `<div>`,看起來像按鈕卻不是連結。改成 `<a>` 連到 `/Works`。
順帶依需求把導覽第二項改名「建立新歌單」。

### 2. 照片上傳太久才進濾鏡

原因有兩層:上傳的是手機原圖(動輒 8–12 MB),而修圖頁的 canvas 又要把那張原圖
**整個下載回來**才畫得出預覽。

修法:**上傳前先在瀏覽器縮圖**(長邊 1600,與修圖頁匯出的 `MAX_EDGE` 同值,
所以成品畫質不變)。附帶效果:送給 AI 的 payload 從十幾 MB 降到幾百 KB。
縮圖失敗就照原檔送——慢一點總比傳不上去好,10 MB 上限仍由伺服器把關。

### 3. 背景圓圈與修圖框沒有對齊

修圖頁右側有 400px 固定側欄,照片框的視覺中心在 `(100% − 400px) / 2`,
而音波環寫死 `left:50%`,偏了約 200px。

修法:CSS 變數 `--iw-center-x`,修圖頁用 `body:has(.iw-edit)` 覆寫成
`calc((100% - 400px) / 2)`。**實測偏移 0 像素。**

### 4. 更多修圖功能

新增三個滑桿 + 色調曲線(等同暗部/亮部,而且更強):

| 控制項 | 實作 | 原點 |
|---|---|---|
| 色溫 | `sepia` + `hue-rotate` 合成(CSS 沒有現成的色溫函式) | **0**(−100 冷 ↔ +100 暖) |
| 銳利度 | SVG `feConvolveMatrix` 3×3 卷積,中心 1+4a、四邊 −a,總和恆為 1 | 0 |
| 柔焦 | `blur(0–8px)` | 0 |
| 色調曲線 | SVG `feComponentTransfer type="table"`,五個控制點可拖曳 | 對角線 |

技術上先在瀏覽器實測 `ctx.filter = 'url(#id)'` 可行(且能與其他 filter 函式串接)
才動手——**canvas 吃 SVG 濾鏡不是理所當然的,要驗過**。

曲線的五個 Y 值**就是** `tableValues`,存進 `PhotoEdit.CurvePoints` 也是同一個字串,
沒有中間轉換層。因為這個值會被寫進頁面的 SVG 屬性,伺服器端有 `NormalizeCurve`
驗證(只接受五個 0–1 的數字,任何一項不合整條退回對角線;用 InvariantCulture,
避免地區設定把逗號當小數點)。

「還原」按鈕要注意:**三個百分比滑桿的原點是 100,新的三個是 0**,不能一律設 100。

### 5. 開啟網頁很 lag

實測拆出兩個獨立原因:

- **前端**:`.iw-glare` 是 920×920 元素套 `filter:blur(46px)` + `mix-blend-mode:screen`
  再做 26 秒無限旋轉——瀏覽器每一幀都要重算整片模糊。改用本身柔和的
  conic-gradient + radial mask,外觀幾乎一樣,動畫只剩 transform(合成器處理)。
  `.iw-scan` 的全螢幕 `mix-blend-mode:overlay` 也拿掉(不透明度 .055,看不出差別,
  成本卻是整頁)。並加 `prefers-reduced-motion` 支援。
- **伺服器**:實測那次 26.8 秒裡有 24.4 秒在等伺服器——那是 AI 判讀還沒持久化
  之前的請求(判讀 + 5 次 YouTube 搜尋)。持久化與快取生效後,同一頁 2–3 秒。

### 6. 判讀完沒有試聽

按鈕和播放器都存在,但 `<iframe src="">`——**空字串的 src 會被解析成當前頁網址**,
而且播放器在視窗外,按了看不到任何反應。

修法:iframe 改為按「試聽」時才動態建立;按下後 `scrollIntoView` 捲到可見位置,
並在按鈕上標示播放中。

### 7. 歌曲播放沒有進度條

播放器是 1×1 px 隱藏的 YouTube IFrame(刻意的,畫面上是自製播放列),
所以 YouTube 原生進度列看不到。自製一條:

- YouTube API 沒有進度事件,**只能輪詢**(500ms 一次)
- 刻度用 0–1000 的相對值而非秒數——換歌不必重設 max,拖曳中的值也不會被新歌長度截掉
- 拖曳中暫停輪詢覆寫(`seeking` 旗標),放開才 `seekTo`
- 實測:總長 4:42 正確顯示,拖到 50% 顯示 2:21

### 8. 新功能:修圖頁取歌單名,並送進 AI 的 prompt

- `Photo.PlaylistName`(nullable,與修圖參數同一次 migration)
- 修圖頁新增輸入欄,說明文字明講「取的名字會一起送給 AI」
- prompt 新增條件段(位置在情緒之後、濾鏡之前):名字是**最強的意圖訊號**,
  但 prompt 同時要求「名字是方向,照片是主體」,避免變成純文字推薦
- 沒取名就整個欄位不送(與情緒同一原則:空字串也是一種錨定)
- 推薦頁的歌單預設名改為優先用使用者取的
- **實測**:命名「夏天的海邊兜風」→ 推薦出現 The Beach Boys、久石讓《海の見える街》、
  keywords 含 beach/ocean;並讀 n8n 執行紀錄確認 prompt 原文含該段文字
