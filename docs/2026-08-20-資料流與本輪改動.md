# 一、資料流

## 全景

```
瀏覽器                InWave (C#)              n8n              外部服務
──────                ───────────              ───              ────────
選檔
 └ canvas 縮圖 ──────► 存檔 + 建 Photo
   (長邊 1600)         wwwroot/uploads/{guid}.jpg
                       Photo / MoodProfile

修圖 (canvas)
 └ ctx.filter 鏈 ────► 存合成圖 + PhotoEdit
   toDataURL           {guid}_edited.jpg
                       + Photo.PlaylistName

進推薦頁 ────────────► 讀「原圖」bytes
                       base64 ──────────────► 組 prompt ──────► 視覺模型
                                              解析回應
                       驗型別、驗 moodPick ◄── {ok, scene, songs…}
                       寫 PhotoAnalysis
                       回填 MoodProfile
                       逐首找影片 ─────────────────────────────► YouTube API
                       寫 SearchCache
勾選 ────────────────► Playlist / Song / PlaylistSong

播放 ◄───────────────  Details 頁                              YouTube IFrame
```

## 逐站說明

### 1・上傳（瀏覽器 → `POST /Works/Create`）

| 進來的 | 出去的 |
|---|---|
| 使用者選的檔案（手機拍的動輒 8–12 MB）| **長邊 1600 的 JPEG**（q0.9），multipart |

**縮圖在瀏覽器做**。長邊 1600 與修圖頁匯出用的 `MAX_EDGE` 是同一個值，所以成品畫質不受影響；
送給 AI 的 payload 也從十幾 MB 降到幾百 KB。縮圖失敗就照原檔送（10 MB 上限由伺服器把關）。

伺服器端產生的資料：

```
檔案   wwwroot/uploads/{GUID}.jpg     ← 檔名重新產生,不用使用者原檔名
Photo         { OriginalPath, CreatedAt }
MoodProfile   { MoodName = "" 或使用者選的, IsAiFilled = false }
```

`MoodName` 用**空字串當「未指定」的哨兵值**——零 migration 的選擇，2026-08-17 定案。

### 2・修圖（瀏覽器 canvas → `POST /Works/Edit`）

canvas **一律載入原圖**。若載入上次的合成圖，濾鏡與滑桿會疊第二層，越修越歪。

濾鏡鏈的組成順序（順序有意義：先銳化再調色，才不會把調色的雜訊一起放大）：

```
url(#iw-sharpen)   SVG feConvolveMatrix,核總和恆為 1
url(#iw-curve)     SVG feComponentTransfer,tableValues = 曲線的五個控制點
brightness / contrast / saturate
sepia + hue-rotate 合成的色溫
blur               柔焦
預設濾鏡           暖陽 / 冷夜 / 褪色
```

送出時 `canvas.toDataURL('image/jpeg', 0.85)` 產生合成圖。伺服器端產生：

```
檔案   wwwroot/uploads/{GUID}_edited.jpg   ← 由原檔名推導,重修就原地覆蓋
PhotoEdit { Brightness, Contrast, Saturation, Temperature, Sharpness,
            Softness, CurvePoints, FilterName }
Photo.PlaylistName                          ← 使用者取的歌單名(可留白)
```

`CurvePoints` 是逗號分隔的五個 0–1 數字，**它就是 SVG 的 `tableValues`**，沒有中間轉換層。
因為這個值會被寫進頁面的 SVG 屬性，伺服器端有 `NormalizeCurve` 驗證。

### 3・AI 判讀（C# → n8n → 視覺模型）

**送出的 payload**（`PhotoAnalysisService`）：

```jsonc
{
  "imageBase64": "…",        // 讀的是 OriginalPath,不是 EditedPath
  "mimeType": "image/jpeg",
  "mood":         "夜色",     // 沒選 → 整個欄位不送
  "filter":       "冷夜",     // 沒選 → 整個欄位不送
  "playlistName": "夏天的海邊", // 沒取名 → 整個欄位不送
  "sliders": { "brightness": 130, "contrast": 100, "saturation": 100 },
  "style": "default"          // 目前只有一個值,是「多種推薦人格」預留的接縫
}
```

**為什麼送原圖**：濾鏡與滑桿以**文字**進入 prompt，送合成圖會讓「暖陽濾鏡」被算兩次。

**為什麼沒選就整段不送**：空字串也是一種輸入，會錨定判讀。欄位不存在，AI 才是真的沒有意見。

**n8n 內部**：`Webhook → Build Prompt → Convert to File → 視覺模型 → Parse → Respond`，
另有一條錯誤輸出接到「AI Unavailable」再匯回 Respond。

prompt = **一段基礎 + 四段條件**，條件段只在使用者表態時才附加：

| 段 | 觸發 | 內容要旨 |
|---|---|---|
| 基礎 | 永遠 | 回傳格式 + 六條規則（要 5 首、要有知名度、曲風要有變化、至少 1 首純音樂、OST 最多 1–2 首、keywords 避開 lofi/radio/mix/24-7）|
| A 情緒 | 有選 | 以使用者指定為準，`moodPick` 直接回傳該值 |
| A2 歌單名 | 有取名 | **名字是方向，照片是主體** |
| B 濾鏡 | 有選 | 讓推薦帶上該風格的色彩 |
| C 滑桿 | 偏離 100 | 只提偏離的那幾項，全預設就整段不送 |

**回來的回應**：

```jsonc
{ "scene": "…", "moodPick": "懷舊", "mood": ["…"], "keywords": ["…"],
  "songs": [{ "artist": "…", "title": "…", "why": "…" }],
  "ok": true, "model": "gpt-4o" }        // ok 與 model 放在展開之後,AI 覆寫不了
```

**C# 端的驗證**（跨越信任邊界的唯一一處）：

```
最外層必須是物件            否則 BAD_JSON
ok 必須是布林 true          字串 "true" / 數字 1 / null 一律視為失敗
error 取不到就用預設值      不丟例外
陣列裡的非字串元素過濾掉
songs 最多取 5 首           模型漂移回 40 首 = 4,000 配額單位
moodPick 必須落在八種內     範圍外換成 null,視為未指定
```

**寫入**：

```
PhotoAnalysis { PhotoId, RawJson, Scene, AnalyzedAt, ModelUsed }
```

混合形狀：整包原文存 `RawJson`，另拆三個常用欄位。**判讀失敗不寫入** ——
留一筆空判讀，那張照片就永遠不會再判讀了。

**回填**：`moodPick` 寫回 `MoodProfile.MoodName` 並標記 `IsAiFilled = true`，
但**只在情緒還沒有值、或現值本來就是 AI 填的時候**。使用者自己選的永遠不動。

### 4・找影片（C# → YouTube API）

AI 給的是「歌手 + 歌名」，YouTube 那端做的是**指名搜尋**，不是氣氛搜尋。

```
1. 查 SearchCaches,鍵 = "song:{artist} - {title}".ToLowerInvariant()
2. 未命中才打 API,maxResults=5,不加 videoCategoryId
   (指名搜尋要的是「那一首」,OST 與動畫歌常在其他分類)
3. 過濾 liveBroadcastContent != "none"
4. 挑選:Topic 且頻道含歌手名 → 含歌手名 → 任何 Topic → 第一筆
5. 寫回 SearchCaches——**連「找不到」也快取**(存空陣列)
```

配額算式：一次搜尋 100 單位，一次推薦 5 首 = 500 單位，每日 10,000 單位 →
**沒有快取的話一天只夠 20 次推薦**。所以快取不是優化，是能不能用的問題。

### 5・存檔與播放

```
Playlist      { Name, PhotoId, CreatedAt }     ← 名稱留白就用「情緒・日期」
Song          { YoutubeVideoId(唯一), Title, Artist, ThumbnailUrl }
PlaylistSong  { PlaylistId, SongId, SortOrder }
```

播放頁用 YouTube IFrame API，播放器本身是 1×1 px 隱藏的，畫面上是自製播放列
（含自製進度條——YouTube API 沒有進度事件，只能輪詢）。

## 資料流的五條規則（會反覆出現的原則）

1. **送 AI 的一律是原圖**，濾鏡與滑桿以文字進入
2. **使用者沒表態的欄位整個不送**，不是送空字串
3. **封閉詞彙的驗證放 C# 端**，不在 n8n 再抄一份清單
4. **判讀失敗不寫入**，讓下次能重試
5. **外部回應一律先驗型別再取值**，並對數量設上限

# 二、本輪改動記錄（2026-08-20）

## A・收藏庫改版

**問題**：只有一份歌單時畫面像壞掉——書背散在中間、照片壓在上面。
根因是 `.iw-shelf` 用 `flex-wrap + align-items:center`，而封面是
`position:absolute` 的 330×420 疊在正中央。

**改法**：書背貼齊底板、不換行、超出橫向捲動；封面移到書架**下方**的
「抽出的那一卷」面板——那才是抽帶子的真實動作，也不會擋住其他書背。

順手修掉三個 PROGRESS 記著但一直沒做的：

- 架上留空位，點空位就是建立新歌單（比 CTA 更符合書架的語彙）
- 選取改成前端切換（舊版寫死第一筆）
- 情緒篩選改成真的會篩，且只列出實際有作品的情緒（舊版是寫死五顆的假按鈕）

另加**底部情緒色帶**：28 種書背款式各自把 `--c` 壓在深色漸層裡約 40% 透明，
小尺寸看不出差別；實色帶讓「哪一卷是什麼情緒」一眼可辨，且對所有款式一致。

## B・導覽收斂

「我的歌單」「播放」「收藏庫」三個都指向 `Works/Index`。
同一個地方三個名字只會讓人猶豫該點哪個。收斂成 **`＋ 建立歌單`** 與 **`收藏庫`**。

## C・刪除用不到的頁面與程式碼

| 刪除 | 證據 |
|---|---|
| `Views/Home/Privacy.cshtml` + `HomeController.Privacy()` | 樣板遺留，沒有任何連結指向 |
| `Views/Shared/_Layout.cshtml.css` | 全是樣板的 `navbar-brand` / `btn-primary`，重寫版面後沒一個選擇器對得上 |
| `wwwroot/css/site.css`（496 行）| 49 個 class 只有 3 個還在用，其餘是改版前的 `mb-*` 遺留 |
| `.iw-spine` 重複規則 | hover / is-on 各有兩組在互相覆蓋 |

保留的三條規則併入 `inwave.css`。**現在自寫樣式只剩一個檔。** 淨減 454 行。

## D・兩個使用者回報

**1・「沒輸入名字會用預設去影響判斷」—— 查證後沒有洩漏**

用完全比照「沒取名、沒選情緒、滑桿全預設」的請求實跑一次，
組出來的 prompt **在基礎段就結束**，三個條件段一個都沒有；資料庫存的也是 `null`。

但誤會是設計造成的：推薦頁會把名稱欄位自動填成「情緒・日期」，
看起來像系統替你取了名字。改成不預填，建議名當 placeholder，留白送出時伺服器端重算。

順帶抓到一個**會讓上述邏輯永遠走不到**的問題：`PlaylistName` 是不可為 null 的 `string`，
MVC 會自動加 required 驗證（輸出裡有 `data-val-required`），留白會被擋在驗證階段。
改成 `string?`。

**2・試聽位置** —— 播放器原本在左欄照片下方，離「試聽」按鈕很遠，視窗不夠高時在畫面外。
移到右欄歌曲清單正上方，預設隱藏，按下才展開。

## E・工作流部署改走 REST API

**問題**：改一次工作流要 `docker cp` → `import:workflow` → **`docker restart`**，
因為 CLI 改的是資料庫，而 webhook 註冊表在記憶體。一次 43 秒。

**實測拆解**（`docker restart n8n`）：

```
 0.0s  SIGTERM
 0.4s  Stopping n8n...
22.0s  Initializing n8n process     ← 光「優雅關機」就 21.6 秒
25.8s  port 5678 ready              ← n8n 本體啟動只花 3.8 秒
43.3s  webhook 真的能處理請求        ← 建索引 + 啟用工作流 + 註冊 webhook
```

對照組（同一個 Docker）：

| | Docker 拉起容器 | 應用程式可用 |
|---|---|---|
| inwave（ASP.NET）| 2.8 s | 9.6 s |
| n8n（Node.js）| 4.7 s | 43.3 s |

**所以慢的不是 Docker**——Docker 只佔約 4 秒。

**改法**：`scripts/deploy-n8n-workflow.ps1` 走 n8n public API
（`PUT /api/v1/workflows/{id}` + `POST /activate`），n8n 會**當場註冊 webhook**，不必重啟。
沒有 API key 時自動退回舊的 CLI 路徑，腳本仍可用。

部署後一定要**探測驗證**：不帶 token 打 webhook 應得 403（Header Auth 擋下）
而非 404（沒註冊）——API 回 200 只代表資料寫了，不代表 webhook 活了。

## F・量測記錄

| 問題 | 量到的事實 |
|---|---|
| SQLite 是不是網站慢的原因？| **不是**。24 筆查詢共 116 ms，平均 4.83 ms，最慢 57 ms，資料庫 112 KB |
| 那 24.4 秒的伺服器等待？| 全部在等 AI 判讀，SQL 佔不到 10 ms |
| n8n 的資料庫有問題嗎？| 有，但是**另一個** SQLite：`n8n-data/database.sqlite` 在 Windows bind mount 上，log 出現 8 次 `Database ping failed: connection timed out` |
| 正式環境能用 Linux 嗎？| **現在就已經是了**——容器內是 Ubuntu 24.04，Windows 只是宿主。C# 裡沒有反斜線路徑或磁碟機代號，`uploads` 大小寫一致 |

**Linux 上要處理的四件事**：`docker-compose.override.yml` 的 `${APPDATA}` 是 Windows 專屬
（已分層，正式部署用 `-f docker-compose.yml` 排除）；**容器目前以 root 執行**（`uid=0`）
應改為非 root；bind mount 的目錄權限要對得上；SQLite 放本機磁碟不要放 NFS。
