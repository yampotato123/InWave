## 1. 背景

MyMusicBuddy 目前是「使用者手選情緒 + 濾鏡 → 規則查表 → 關鍵字 → YouTube 搜尋」的流程，
完全沒有 AI 參與，也沒有容器化。

這輪要做兩件事：

1. **學習目標**：正確使用容器（Docker）、學會 n8n。這是主要動機，不是附帶。
2. **功能目標**：把「照片內容」納入推薦依據，讓 AI 判讀照片而不只依賴使用者手選的 8 種情緒。

兩者在這輪合併進行，因為 AI 判讀放在 n8n 裡執行，剛好同時服務兩個目標。

---

## 2. 目標與非目標

### 目標

- MyMusicBuddy 能在容器中執行，資料（SQLite + 上傳照片）不會因容器重建而消失
- n8n 與 MyMusicBuddy 在同一個 compose 中，能互相通訊
- 按下「確認」後，由 n8n 呼叫視覺模型判讀照片，產生搜尋關鍵字
- n8n 不可用時，功能自動回落至現有 `MoodKeywordMapper`，不中斷

### 非目標（本輪明確不做）

| 項目 | 理由 |
|---|---|
| **Qdrant 向量資料庫** | 目前音樂來源是 YouTube 搜尋 API，沒有自有音樂庫，向量檢索無對象。詳見 §3.4 |
| **聊天機器人** | 學習用 lab，非產品需求。架構會留接口，之後接很快 |
| **CDN / 物件儲存** | 屬上架階段議題。照片仍寫入 `wwwroot/uploads/`，用 volume 保住 |
| **正式部署** | 本輪只到本機 compose |
| **改名成 InWave** | 與本輪無關，見 `PROGRESS.md` 待辦 |

## 3. 架構決策

### 3.1 整體架構：n8n 當 AI 後台

```
瀏覽器
  │ 上傳照片、選情緒、修圖
  ▼
MyMusicBuddy (容器)
  │ 按下確認 → POST 原圖 + 情緒 + 濾鏡
  ▼
n8n (容器)
  │ 視覺模型判讀 → 產生關鍵字
  ▼
MyMusicBuddy ──→ YouTube Data API ──→ 推薦結果
```

**選這個而非「C# 直接呼叫 AI」的理由：**

1. n8n 是必學項，這個架構讓它當主角而非排程器
2. C# 改動最小——照 `Program.cs:13` 現有 `AddHttpClient<IYouTubeService, YouTubeService>()` 的 typed client 模式新增一個服務即可
3. prompt 迭代成本低。AI 功能的 prompt 會反覆修改數十次，在 n8n 中改完存檔即生效；在 C# 中每次都要重建映像檔並重啟容器
4. n8n 的執行歷史保留每一步的輸入輸出，AI 除錯時這是決定性優勢
5. 模型 API 金鑰只存在 n8n 一處，C# 端不需要管理

**已知代價：** 多一跳（延遲較高）；n8n 故障會影響推薦——以 §3.5 的 fallback 處理。

### 3.2 AI 判讀的輸入：原圖 + 使用者選擇（文字）

**修訂 `PROGRESS.md:158-160` 的既有規則。**

舊規則寫的是：

> **AI 情緒判讀的規則（日後接時務必遵守）**：AI 讀原圖，不讀修圖後的圖。
> 否則暖陽濾鏡會被計算兩次——一次 AI 看到偏橘判成「溫暖」，一次修飾詞又加了 `warm`。

舊規則的意圖正確（避免重複計算），但表達成禁令，且仍保留「AI 輸出 + 濾鏡修飾詞」的事後字串拼接。
本輪改為正面規格：

> **AI 一次判讀，輸入為「原圖」加上「使用者選擇的結構化文字」（情緒、濾鏡主題、滑桿數值）。
> 輸出即為最終關鍵字，不再事後拼接修飾詞。**

**為什麼不讓 AI 直接讀修圖後的圖（曾考慮的替代方案）：**

| 問題 | 說明 |
|---|---|
| 配額與快取 | 每次重修圖片都會改變 AI 輸入 → 關鍵字改變 → `SearchCaches` 失效。YouTube 每天僅 100 次搜尋額度（`README.md:31`），且視覺模型本身也要計費 |
| 使用者意圖流失 | 使用者選「冷夜」是明確表態「我要夜的感覺」。若只是薄薄一層藍調，AI 可能仍判為晴天海灘，該訊號無保證被接收 |
| 測試失去著力點 | 現有 18 項測試涵蓋「情緒 × 濾鏡」所有組合，成立前提是 `MoodKeywordMapper` 為確定性函式。若濾鏡影響經過 AI，斷言只能退化成 not-null 等級 |

濾鏡以**文字**（例如「賽博朋克」）而非**像素**進入 AI，語意密度也遠高於色調變化。

**觸發時機：使用者按下「確認」才呼叫 AI。** 修圖過程中的反覆調整不觸發，成本與快取問題一併解決。

### 3.3 Agent 放在 n8n

若日後引入能自行決定呼叫哪些工具的 agent，位置定為 n8n。理由同 §3.1 第 3、4 點：
prompt 迭代成本與除錯可視性是 AI 功能的決定性因素。

待 prompt 穩定、確認不再頻繁修改後，再評估是否移入 C#（屆時已知正確答案，屬照抄而非摸索）。

### 3.4 Qdrant 延後的理由

向量資料庫解決的是「在自有資料集中尋找相似項目」。目前：

- 音樂來源是 YouTube 搜尋 API，非自有音樂庫 → 無檢索對象
- 完整路徑「照片 + 濾鏡 → AI → 關鍵字 → YouTube 搜尋」不需要向量參與

Qdrant 產生價值的時機（皆非本輪）：

1. 「找出與此作品氣氛相似的**其他作品**」——需先累積作品量
2. 「從**已收藏的歌**中挑選，而非每次呼叫 YouTube」——需先累積歌單

附帶觀察：`MoodProfiles` 已有 Energy / Calmness / Warmth / Exploration 四個數值欄位
（`README.md:77`），本質上已是四維向量。日後導入 embedding 屬同一概念的延伸，非全新機制。

### 3.5 失敗處理

n8n 無回應、逾時或回傳格式錯誤時，**回落至現有 `MoodKeywordMapper`**。

這使 AI 成為加分項而非單點故障，且現有 18 項測試全數保持有效。
回落發生時須寫入 log，不可無聲吞掉（否則無法得知 AI 是否真的在運作）。

## 4. 分階段計畫

原則：**每一階段結束都是可用狀態。** 時間不足即停在該階段，不留半成品。

### 階段 0 — 基準線（30 分鐘，使用者自行執行）

```powershell
dotnet build
dotnet ef database update
dotnet run --launch-profile https
```

**驗收**：能上傳照片、選情緒、修圖、取得推薦（回 `[示範]` 資料亦算通過）。

此為後續所有階段的參照點。缺少它，容器中出錯時無法區分是 Docker 問題或 App 既有問題。

### 階段 1 — MyMusicBuddy 容器化（1–1.5 天）

撰寫 `Dockerfile`（多階段建置：SDK 編譯 → runtime 執行）與 `docker-compose.yml`。

預期會遭遇的三個問題（皆為既有程式碼與容器環境的真實衝突）：

| 問題 | 位置 | 處理方向 |
|---|---|---|
| `UseHttpsRedirection` 在僅開放 http 的容器中造成轉址失敗 | `Program.cs:23` | 容器內走 http，轉址交由外層處理 |
| User Secrets 在容器中不存在，YouTube 金鑰讀不到 | `.csproj:7` | 改用環境變數注入 |
| `mymusicbuddy.db` 與 `wwwroot/uploads/` 隨容器刪除而消失 | `PROGRESS.md:154` | 掛載 volume |

**驗收**：`docker compose up` → 瀏覽器可開啟 → 上傳一張照片 →
`docker compose down` 後再 `up` → **照片與資料庫內容仍在**。

**學習重點**：映像檔、埠對應、volume、環境變數。

### 階段 2 — n8n 納入同一個 compose（半天）

將現有 `C:\Users\admin\source\repos\n8n0807` 的 n8n 正式移入本專案的 compose。

**注意**：`C:\Users\admin\source\repos\Docker\n8n\n8n_storage` 是 2026-08-10 的舊快照，
`n8n0807\n8n_storage` 才是現行資料。搬移須以後者為準，且搬移前備份。

**驗收**：兩容器位於同一網路，MyMusicBuddy 容器內可透過 `http://n8n:5678` 連到 n8n。

**學習重點**：容器網路、服務名稱作為 DNS、容器內的 `localhost` 為何不等於主機的 localhost。

### 階段 3 — AI 判讀接上（1–1.5 天）

**n8n 側**：webhook 接收「原圖 + 情緒 + 濾鏡主題 + 滑桿數值」→ 視覺模型判讀 → 回傳關鍵字 JSON。

此處的「濾鏡主題」為**現有三種濾鏡**（暖陽 / 冷夜 / 褪色）的名稱。
階段 4 若執行，僅是往這份清單增加項目，n8n 工作流與 C# 介面皆不需改動；
階段 4 若砍除，階段 3 仍完整可用。

**C# 側**：新增 `IRecommendService`（照 `Program.cs:13` 的 typed client 模式），
於「確認」動作中呼叫。失敗時依 §3.5 回落。

**驗收**：
- 按確認 → 取得 AI 產生的關鍵字 → YouTube 有搜尋結果
- 停掉 n8n 容器後功能仍可用（走 fallback），且 log 有記錄

**學習重點**：n8n 工作流、容器間 HTTP 通訊、AI prompt 迭代。

### 階段 4 — 主題濾鏡（選配，1 天）

新增賽博朋克 / 東京 / 懷舊電影等主題濾鏡。純 C# + CSS，不涉及 Docker。

定義集中於 `Services/PhotoFilters.cs`（維持單一來源，見 `README.md:67`）。
新增濾鏡須同步補上對應測試。

**排在最後的理由**：不服務本輪兩個必學項。時間不足即砍除，或僅實作一個濾鏡。

### 砍除順序

```
階段 4  ← 先砍
階段 3  ← 再砍（代價：n8n 只學到一半）
階段 1、2 ← 不可砍，此即學習目標本身
```

## 5. 已知風險

| 風險 | 影響 | 處置 |
|---|---|---|
| Google Fonts CDN 在容器中連不上 | `_Layout.cshtml:14` 載入 6 個字體家族。連不上時不會報錯，只會靜默 fallback 成系統字體，InWave 視覺走樣 | 階段 1 驗收時明確檢查字體是否正確載入 |
| 首次容器化耗時超估 | 階段 1 可能吃掉 2 天 | 階段 4 為緩衝，可整段砍除 |
| 視覺模型判讀結果不理想 | 照片描述無法對應到合適音樂 | 階段 3 先手動在 n8n 中以 3 張照片試跑，確認可行再接 C# |
| SQLite 檔案鎖定 | 容器與本機同時存取同一 `.db` 會出現 `database is locked` | 容器執行期間不同時跑 `dotnet run`（見 `README.md:98`） |
| n8n 搬移弄錯資料版本 | 既有 workflow 遺失 | 搬移前備份；以 `n8n0807` 為準，非 `Docker\n8n` 的舊快照 |
